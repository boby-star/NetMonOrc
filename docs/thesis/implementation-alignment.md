# Узгодження записки з програмним прототипом

Цей текст підготовлено як матеріал для фінального редагування записки,
а не як твердження, що завантажений DOCX уже автоматично змінено.

## Реально реалізований метод

Програмний прототип збирає різнорідні результати HTTP, TCP і DNS з двох
логічно розділених мережевих зон. Для стандартних перевірок використовується
Blackbox Exporter, а обмежений native HTTP runner дозволяє витягувати
прикладні значення. Controller окремо перевіряє походження спостереження,
його конфігураційну ревізію, часову актуальність і результат виконання.
Це дозволяє не ототожнювати відмову інструмента зі збоєм контрольованого сервісу.

Комплексне оцінювання використовує вагову успішність H та повноту Q.
Обов'язкова негативна перевірка визначає down незалежно від високого H;
нестача актуальних доказів дає unknown. Зональні висновки об'єднуються
за all-required. H і Q є показниками визначеної моделі, а не оцінками
ймовірності безвідмовної роботи. CEL уточнює оцінку, зберігаючи ці інваріанти.

При несправності діагностика обирає допустиму пару «перевірка–Agent».
Adaptive оцінює кількість ще нерозрізнених пар гіпотез на одиницю вартості.
Static виконує весь каталог, Fixed — заданий DAG. Усі режими мають ті самі
дії та бюджетні обмеження. Додаткові підтвердження враховують різні відомі
failure domains і часові умови. Повтор technical failure витрачає той самий
бюджет і не створює нового доказу про стан сервісу сам по собі.

## Результати, які вже можна наводити

Повторна серія містить 30 запусків: два повтори п'яти сценаріїв у трьох
режимах. У цій серії всі 30 станів та діагностичних результатів відповідали
заданому сценарію. Це 24 визначені одиничні класи й 6 inconclusive для
поєднаної HTTP+DNS несправності. Коректний inconclusive не слід називати
правильно визначеною фізичною першопричиною. Сирі дані та описова статистика:
[repeated-series](../experiments/repeated-series/README.md).

У цій серії Static виконував 6 probes, а confirmed Fixed та Adaptive — по 4.
Отже, за кількістю перевірок показано скорочення порівняно зі Static,
але не перевагу Adaptive над Fixed. Медіани й діапазони часу подано окремо
для кожного сценарію. Два повтори на спільному хості не дають підстав
стверджувати статистичну значущість або універсальну точність методу.

Попередній early-stop пілот містив два хибні визначені класи для HTTP+DNS.
Ці результати не видалені. Explicit confirmation усунуло саме цей відомий
контрприклад у наступних контрольних прогонах. Не слід приховувати початкову
помилку або стверджувати, що confirmation усуває будь-яку множинну несправність.

## Межі тверджень

Точки спостереження мають різні маршрути, але один фізичний Docker-хост.
У профілі один Agent на зону; експерименту з різними quorum-порогами немає.
ResourceGroup і довільний граф Dependency не реалізовані як перевірені
компоненти цього мінімуму. Їх можна залишити як можливий розвиток моделі.
ICMP перевірявся окремим ізольованим smoke, а не всією повторною серією.

Метод не гарантує знаходження першопричини поза заданим каталогом гіпотез.
Мережеві байти не вимірювалися; costUnits не можна використовувати замість
реального трафіку. Час Engine.Run не включає затримку до запуску діагностики.
Доставка webhook допускає повтори одного event_id, а не exactly-once.
BOOTTIME перевіряється перед новими probes; фактичний suspend ОС у Cloud
не виконувався. Збережені конфігурації не запускаються після рестарту без
нового lease. UI є приватним read-only HTML-звітом, а не повною React-панеллю.

Точні межі приймання: [prototype-acceptance](../planning/prototype-acceptance.md).
