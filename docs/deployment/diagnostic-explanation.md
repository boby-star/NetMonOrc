# Пояснення діагнозу та відкриття доказів

У React відкрийте «Діагностичні сесії» → «Оновити список» → «Відкрити».
Деталі показують збережену ревізію сесії й журнал фактичних рішень Controller:
дію, Agent, спробу, фазу, гіпотези перед кроком, gain/score та окремі execution
і probe результати. Далі показані costUnits, час Engine.Run, confirmation,
заблоковані та пропущені fixed steps. Це пояснює історичний діагноз, а не
обчислює поточний стан Monitor у браузері.

Активна сесія оновлюється через 3 секунди після завершення попереднього
читання; прапорець дозволяє вимкнути це. POST start/cancel автоматично не
повторюються. Кнопка «Завантажити сесію JSON» зберігає поточний snapshot
деталей, включно з поясненням; це не архів raw observations або backup БД.

Повний збір завдань та Observation: [пакет доказів](diagnostic-export.md).

## API та CLI

Наявний `GET /api/v1/diagnostics/{id}` зі scope `diagnostics:read` повертає
додаткові поля `configRevision` та, за наявності збереженого журналу,
`explanation`. Таблиця рішень зберігає порядок Controller. Списки сесій і
Dashboard не включають explanation; для нього потрібно відкрити конкретну
сесію. Raw report, конфігурація перевірки, ціль, body і приватні поля не
передаються — використовується окрема типізована проєкція.

```sh
netmonorc get --context-file /private/context.json diagnostics SESSION_ID
```

CLI повертає ті самі нові поля без окремої команди. Legacy report без decisions
або сесія без завершеного звіту не отримує вигаданого журналу. Відомий порожній
журнал `decisions: []` відрізняється від його відсутності. Нульовий duration,
score та незадоволена confirmation зберігають своє значення.

Gain — кількість розрізнюваних пар гіпотез, score — gain / costUnits.
Fixed/Static мають власний порядок виконання, незалежний від максимального
score. CostUnits не є байтами; duration не включає очікування автоматичного
trigger; execution_failed не є доказом несправності сервісу. HypothesesBefore
описує стан саме перед кроком; кінцеві гіпотези наведені окремо. Журнал не
реконструюється з поточного профілю, який уже міг змінитися.

## Зв'язок із Observation

«Відкрити доказ» доступне в зональній оцінці, деталях алерту, фізичних
діагностичних задачах та історії перевірок зі scope `resources:read`.
Відкривається саме збережений ID. Старий/видалений retention доказ не
підміняється новішим результатом; помилка читання показується явно.

## Перевірка цієї ітерації

Пройшли цільові Go suites storage/httpapi/apiclient, тест проєкції
(technical failure, нулі, legacy/empty journal, відсікання приватних полів),
реальний PostgreSQL/HTTPS `TestPostgresBrowserSessionsAndCSRF` із перевіркою
нового detail та відсутності explanation у списку, production React build.
Повні натурні серії й browser acceptance попередньої ітерації повторно не
запускалися; нові кліки та auto-refresh у браузері цією ітерацією не підтверджені.

## Часова придатність

Нові звіти показують policy TTL/maxSkew та physical finishedAt/validUntil кожного
отриманого доказу. Докладно: [часове вікно](../architecture/diagnostic-evidence-window.md).
Колишні натурні серії залишаються історичними; їх не слід подавати як новий
запуск із цією temporal policy.
