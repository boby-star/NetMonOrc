# Керування користувачами (R5)

Реалізовано чотири наявні операції OpenAPI: список користувачів, створення,
читання одного запису та PATCH role/disabled. Видалення і reset чужого пароля
не передбачені цим контрактом і не додаються. Bootstrap першого admin
залишається локальним netmonorc-admin; повторний bootstrap не переписує users.

## Панель

Увійдіть як admin. Розділ «Користувачі» дозволяє:

- Переглянути імена, ID, ролі й ознаку блокування, перейти між сторінками.
- Створити viewer/admin з початковим паролем. Передайте пароль новому
  користувачу захищеним каналом; він може змінити власний пароль у панелі.
- Відкрити запис, вибрати роль або disabled та зберегти зміни.

Ім'я — 1..64 байтів UTF-8, без крайніх пробілів і control characters.
Початковий пароль — 16..256 байтів UTF-8. Він передається лише в HTTPS JSON,
хешується Argon2id, не входить до UserView і очищується з форми після запиту.
Повторне ім'я відхиляється з 409. Паролі/хеші не повертаються у списку чи GET.

Останнього активного admin не можна заблокувати або перевести у viewer.
Сервер перевіряє це в транзакції під спільним advisory lock для mutations
users; два одночасні запити не обходять цю умову. До активних належать
admin із disabled=false. Невдала спроба повертає 409 і не змінює запис.

Будь-яка зміна ролі або перехід до disabled=true атомарно відкликає всі
cookie-сесії та PAT цільового користувача. Повторне ввімкнення не відновлює
старі credentials: потрібний новий парольний вхід та нові PAT. Самостійна
зміна своєї ролі/блокування завершує сесію адміністратора; панель пропонує
увійти знову. Якщо це останній admin, зміна відхиляється.

## HTTP API

| Запит | Успіх |
|---|---|
| GET `/api/v1/users?limit=50&cursor=...` | PageUsers, без credentials |
| POST `/api/v1/users` | 201 UserView, ETag, Location |
| GET `/api/v1/users/{id}` | UserView та сильний ETag |
| PATCH `/api/v1/users/{id}` | UserView та новий ETag |

Для всіх операцій потрібні одночасно роль admin і scope system:admin.
Це browser cookie або відповідний PAT. Cookie mutations вимагають
X-CSRF-Token та same-origin. Bootstrap reader не має доступу до Users.
PAT тільки з resources:read також не надає доступу, навіть власнику-admin.

PATCH приймає role та/або disabled, без null і без невідомих полів. Перед
ним прочитайте GET запису та передайте отриманий ETag у If-Match. Сервер
повторно перевіряє credential, поточну роль і стан адміністратора всередині
транзакції перед зміною. Відсутній If-Match дає 428, застарілий — 412;
після 412 відкрийте запис заново й перевірте зміни перед повторним save.
Wildcard та набори ETag не підтримуються: потрібний один сильний ETag.
Порожній PATCH — 422. Навіть прийнятий patch без зміни значень видає нову
версію, але не відкликає credentials без зміни ролі/блокування.

Список: limit 1..200 (default 50), ID DESC, nextCursor — непрозорий ключ
останнього ID. Він відображає live-дані, не транзакційний snapshot усіх
сторінок. createdAt для старих користувачів до міграції пропускається;
час їх створення не вигадується. Нові users мають збережений час створення.
Успішні create/patch записуються до identity audit з actor username і target ID,
без пароля. Читання обмежене admission slot; хешування створення ділить
один слот і rate budget із password login/change.

## Перевірка та межі

`python3 scripts/identity_smoke.py` виконує один критичний тест із реальною
PostgreSQL/HTTPS. Users cases: створення й вхід нового user, duplicate/CSRF,
viewer та scope RBAC, ETag 428/412, блокування, роль, незворотне відкликання
старих credentials після повторного ввімкнення, пагінація та конкурентні
спроби заблокувати двох останніх admin. Це додається до наявних identity/PAT/
history cases. Не є тестуванням усіх можливих комбінацій UI.

Users UI збирається TypeScript/Vite. Автоматичні browser DOM clicks не
перевірялися. Загальний audit API, resource/config CRUD та інші ще не
реалізовані частини специфікації не позначаються завершеними цим етапом.
