# Повний пакет діагностичних доказів

Завершену сесію (`completed`, `inconclusive`, `cancelled`) можна зберегти
разом із журналом, усіма сторінками фізичних завдань та їхніми Observation.
Результат придатний для офлайн-аналізу й відтворюваного додатка до дослідження.
Нових HTTP routes немає: клієнти використовують наявні read endpoints.

## CLI

```sh
netmonorc diagnostics export --context-file /private/context.json \
  --output .local/incident-001/evidence.json --timeout 2m SESSION_ID
```

Потрібні PAT scopes `diagnostics:read` та `resources:read`. Flags розташовуються
перед ID. Наявний файл не перезаписується. Запис публікується тільки після
успішного збору, mode 0600; помилка мережі/доступу/перевірки походження не
залишає часткового результату. Timeout: 1s–5m, default 2m. Повторюються лише
GET за HTTP 429/503 в межах deadline. POST не виконується.

## React

«Діагностичні сесії» → відкрити завершену сесію → «Завантажити пакет доказів».
Під час збору видно статус, інші операції панелі сесії заблоковано. Вихід
із панелі скасовує запит. «Завантажити сесію JSON» залишається окремою
можливістю отримати лише поточні деталі без завантаження всіх доказів.

## Формат schema 1

- `collectedAt` — UTC час завершення збору;
- `session` — серверний DiagnosticSession із configRevision/explanation;
- `tasks` — всі прочитані фізичні завдання;
- `observations` — збережені нормалізовані результати за точними ID;
- `missingObservationIds` — ID, для яких detail API повернув 404;
- `complete` — усі збережені посилання на Observation вдалося прочитати.

`complete=true` не означає, що кожна reserved task була виконана, що кожна
перевірка успішна або що діагноз правильний. Задача без observation залишається
задачею без observation. За retention 404 записується явний неповний пакет;
403, 5xx після вичерпання retries та транспортні помилки не маскуються під
відсутній доказ. CLI друкує complete і число відсутніх ID; React показує статус.

Клієнт перевіряє session/task/Monitor/Agent provenance та повторення cursors.
Якщо фінальне читання сесії відрізняється від початкового, export відхиляється
з пропозицією повторити. Читання послідовні, **це не атомарний snapshot БД**:
пізні task receipts і retention можуть змінити дані між запитами. Для повного
відновлення системи потрібен окремий PostgreSQL backup.

Обмеження: 1000 tasks, 10000 посилань на докази та 32 MiB на пакет; browser
має загальний deadline 2m. Точні JSON integer values, зокрема поза 2^53,
зберігаються: CLI використовує raw JSON, браузер включає оригінальний текст
Observation без перетворення його чисел на JavaScript number. Для власного
аналізу пакета використовуйте parser з підтримкою int64/decimal.

Сертифікати, PAT, приватні ключі, target/check config, raw HTTP body та DSN
не експортуються. Пакет містить лише дозволені сервером DTO, проте це
приватні дані моніторингу — зберігайте його разом з іншими матеріалами стенда.

## Початкові регулярні докази (§2.1–2.3 записки)

Нові завершені звіти мають `explanation.baselineEvidence`: вхідні регулярні
Observation, зіставлені з діями профілю перед виконанням діагностики.
Для кожної відповідності збережено actionId, фактичний checkId, Agent/zone,
історичну effective revision, відомий failureDomain, finishedAt, validUntil
та execution/outcome. Це історичний вхід сесії, а не твердження, що кожен
результат залишився придатним до завершення: TTL/latest-pair/maxSkew
продовжують застосовуватися окремо.

Відомий порожній набір записується як `[]`. Для legacy/перерваного запуску
без збереженого набору поле відсутнє; він не реконструюється з поточного
Assessment чи конфігурації. Деталі сесії у React показують початкові докази
та дозволяють відкрити точний Observation за наявності resources:read.
Списки сесій не завантажують повне пояснення.

CLI/React додають ці Observation до `observations`, навіть коли висновок
отримано без додаткових tasks та без витрат бюджету. Якщо один фізичний
результат відповідає кільком еквівалентним діям, усі відповідності залишаються
у поясненні, а сам Observation експортується один раз. Регулярний доказ
повинен мати порожні diagnosticSessionId/taskId та збігатися з історичними
Monitor/revision/Agent/check/zone/time/execution/outcome. Діагностичні докази
натомість перевіряються за власною session/task provenance. Змішування цих
двох походжень відхиляється.

Schema 1 доповнено `baselineEvidenceKnown`: true означає збережений набір
(зокрема порожній), false — відсутність такої інформації в історичному звіті.
`complete` як і раніше описує доступність відомих посилань, а не повноту
незбереженої історії. CLI виводить цей прапорець, React окремо пояснює
невідомий склад legacy baseline. Retention 404 для baseline також створює
`missingObservationIds`/complete=false; інші помилки припиняють export.
