# Вхід і зміна пароля у вебпанелі

HTTPS listener Controller повинен бути ввімкнений; у research Compose він працює
всередині приватної мережі. Локальну публікацію додає
`deployment/web-panel.compose.yaml` (127.0.0.1:8443). Використовуйте довірений
сертифікат Controller; перевірку TLS не вимикати. Це користувацький HTTPS,
окремий від агентського mTLS/gRPC.

## Перший адміністратор

На вже запущеному стенді виконайте (PROJECT — назва вашого Compose project):

```sh
docker compose -p PROJECT -f compose.yaml exec controller \
  /usr/local/bin/netmonorc-admin \
  -database-file /run/netmonorc/database.dsn -username admin
```

Команда запитує пароль
без відображення символів. Пароль: 16..256 байтів UTF-8. Не передавайте його
через аргументи командного рядка, environment або YAML. `-password-stdin`
призначений лише для захищеного каналу автоматизації. Повторний bootstrap
не змінює користувача чи пароль: створення можливе лише коли таблиця users порожня.
Це не механізм аварійного скидання пароля.

У панелі виберіть «Обліковий запис». Після входу браузер отримує Secure,
HttpOnly, SameSite=Strict cookie строком 8 годин. Пароль не зберігається у
localStorage/sessionStorage. `/api/v1/auth/me` відновлює відображення після
оновлення сторінки або перезапуску Controller. Сесії зберігаються PostgreSQL;
у БД є лише SHA-256 токена сесії. Хеш пароля — Argon2id (64 MiB, 3 проходи,
один потік, випадкова 16-байтова salt). Доступні viewer/admin; сервер читає
актуальну роль та disabled зі сховища для кожної сесії.

## Зміна власного пароля

У панелі розкрийте «Змінити власний пароль». Введіть поточний та новий пароль.
Ця операція доступна обом ролям і не змінює роль. Успіх атомарно зберігає новий
хеш, відкликає всі старі cookie-сесії цього користувача й створює нову поточну
сесію з новим CSRF-токеном. Інші вкладки повинні увійти знову. Якщо відповідь
втрачена після успішного commit, повторно увійдіть з новим паролем.

REST операції:

| Запит | Результат |
|---|---|
| POST `/api/v1/auth/login` з username/password | SessionView та cookie |
| GET `/api/v1/auth/me` | SessionView чинної cookie-сесії |
| POST `/api/v1/auth/change-password` | currentPassword/newPassword; нова сесія |
| POST `/api/v1/auth/logout` | 204 та відкликання поточної сесії |

Для двох останніх потрібні cookie та `X-CSRF-Token` із SessionView. Сторонній
Origin відхиляється. CSRF-токен виводиться HMAC із токена сесії та не є її
заміною. Неправильний пароль або прострочена сесія: 401; відсутній/неправильний
CSRF: 403; недопустимий новий пароль: 422; обмеження навантаження: 429.
Не включайте cookie, паролі та CSRF у логи/знімки для публікації.

## Захист ресурсу Controller

Хешування для login і password-change ділить один слот та ліміт 20 спроб/хвилину
в процесі. П'ять помилок пароля блокують наступні парольні операції для
користувача на 15 хвилин; стан блокування зберігається PostgreSQL. Вхід, вихід,
bootstrap та зміна пароля мають audit-записи без credentials. Ці межі — локальна
політика реалізації, не нові YAML-поля. Агенти не використовують користувацькі сесії.

## Фактичні межі

Опціональний bootstrap bearer залишається окремим доступом лише для читання
Assessment; він не є PAT та не підтримує `/auth/me`. Реєстрація користувачів,
users CRUD, PAT та авторизація решти майбутніх REST операцій ще не реалізовані.
Зміна пароля наразі відкликає cookie-сесії; PAT з'являться окремою ітерацією.
Реальні HTTPS/PostgreSQL сценарії перевірені; кліки в браузері автоматично не тестувались.
