# YAML-пакети через REST та React

Пакет з того самого формату, що [стартовий каталог](bootstrap-catalog.md),
можна перевірити й застосувати без перезапуску Controller. У React відкрийте
«Конфігурація моніторингу» → «Пакетне застосування й операції», вставте YAML
із документами через `---` або ConfigBatch JSON.

1. «Перевірити пакет» перевіряє схему, типи, посилання та граф у поточному каталозі.
2. «Підготувати пакет» заповнює відсутні expectedVersions і requestId. Результат
   показано як JSON для перегляду. Ресурси ще не створюються й не змінюються.
3. «Показати план пакета» показує створення/заміни, залежні revisions і placement.
4. «Застосувати пакет» використовує атомарний apply та відстежує Agent acknowledgements.

Підготовка не повертає перевагу старому bootstrap файлу: застосування працює
з каталогом БД та чинними optimistic preconditions. Дані агента й діагностики
не створюються самим parser або prepare.

## Версії та повторення

Якщо expectedVersions для ресурсу відсутня, prepare читає його поточну
resourceVersion; для нового ставить null (create-only). Явно задана null або
версія залишається незмінною, навіть якщо ресурс уже існує чи версія застаріла.
Підготовка не приховує конфлікт і не отримує блокування до майбутнього apply.
Зміна каталогу між prepare/plan/apply може дати 409 або 412; тоді треба перевірити
актуальний ресурс і свідомо оновити умови запиту.

За відсутнього requestId генерується випадковий 128-bit ключ. Явний requestId
зберігається; повторне prepare готового пакета дає той самий текст і ключ.
Незмінний apply з тим самим ключем у межах idempotency window (24 години)
відновлює ту саму durable операцію. Для
іншої зміни потрібен новий requestId. Редагування тексту в React скидає стан
підготовки; повторна підготовка не підміняє вже задані умови свіжішими.
«Підготувати пакет із відкритого маніфесту» зберігає версію завантаженого ресурсу.

## Числові типи та детермінованість

React передає текст серверу без JSON.parse/stringify маніфестів. Це зберігає
float `1.0` і integer `9007199254740993`: JS number не використовується для їх
транспортування. Prepare сортує ключі з json.Number, не перетворюючи їх на
float64; порядок масивів, включно з manifests, зберігається. Готовий JSON
передається як текст тим самим шляхом. Integer parameter зі значенням `200.0`
не має ставати допустимим через браузерне округлення до `200`.

Числові та structural bounds залишаються відповідними DSL: <=1 MiB вхідного
тіла, 1..20 manifests, обмеження YAML aliases/depth, заборона merge, duplicate
keys та невідомих полів. Результат prepare теж має вкладатися в 1 MiB; великий
розгорнутий пакет, який не можна відправити назад, відхиляється. Порядок YAML
документів не визначає resolution refs, але для idempotent replay зберігайте
незмінний пакет та порядок manifests.

## REST

| POST endpoint | Результат |
|---|---|
| `/api/v1/config/prepare` | `{source, requestId, resourceCount, documents}`; source — канонічний ConfigBatch JSON як рядок |
| `/api/v1/config/validate` | Перевірка каталогу з valid/errors/warnings |
| `/api/v1/config/plan` | Пропоновані зміни та placement |
| `/api/v1/config/apply` | Durable operation, HTTP 202; той самий атомарний apply |

Для YAML приймаються application/yaml, application/x-yaml, text/yaml. Можна
надіслати один manifest, документи через `---` або ConfigBatch. YAML apply
вимагає непорожній requestId; raw manifest спочатку потрібно підготувати.
Для application/json старі validate/plan/apply й далі приймають ConfigBatch;
prepare також приймає один JSON manifest. Синтаксичні помилки повертають 400,
невідповідність spec — validation errors або 422, конфлікт версії — 412.

Усі операції потребують admin/resources:write, чинної сесії/PAT та same-origin;
для cookie-сесії потрібен CSRF token. Prepare використовує ту саму обмежену
чергу й timeout, що керування конфігурацією. Автоматичного повторення POST немає.

[Редактор одного ресурсу](yaml-editor.md) також підтримує YAML і серверне
текстове подання без втрати точності чисел. Це не зміна алгоритму
Assessment, probe runner або YAML DSL і не повна сертифікація старого ТЗ.
