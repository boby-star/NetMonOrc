# Резервне спостереження як початковий доказ діагностики

§2.1–2.4 актуальної записки вимагають повторного використання придатних
спостережень зі збереженням походження, фактичної точки виконання та бюджету.
Controller тепер допускає до MatchBaseline результат same-zone fallback,
який уже допущений Store.Latest до поточного набору спостережень.

## Допуск і детермінованість

Застосовуються чинні revision, freshness, maxSkew, topology epoch та exact
check-equivalence gates. Додатково потрібні Controller-owned fallback run ID,
первинний Agent, observationId=taskId і відповідність поточній fallback policy.
Ці внутрішні атрибути не приймаються із JSON Agent: сховище додає їх за
збереженим коренем і завданням. Store.Latest відкидає резервний результат,
якщо він більше не відповідає актуальному первинному спостереженню; для
agent_unreachable без Observation перевіряється відсутність новішого regular.

У доказі agentId, zone і failureDomain належать фактичному виконавцю.
Первинний Agent зберігається окремо: він не стає другим незалежним джерелом.
Placement діагностичної дії також перевіряється за фактичним виконавцем.
Технічна помилка не перетворюється на success/failure цілі. Результати
міжзонного fallback до baseline не допускаються.

Коли кілька еквівалентних Check відповідають одній дії й одному фізичному
Agent, обирається один доказ: найбільший finishedAt, потім найбільший
observationId за лексикографічним порядком. Порядок обходу Go map не впливає
на результат. Один Observation може відповідати різним діям профілю, але
експортується один раз. TTL/skew і підтвердження під час сесії лишаються чинними.

## Походження у REST, React та експорті

BaselineEvidence та історичний Observation мають optional fallbackRunId,
fallbackTaskId, fallbackOriginAgentId. REST отримує origin через durable
fallback root, а не з поточних labels. React показує резервне походження поряд
із фактичним Agent та дозволяє відкрити Observation. CLI/React export звіряють
усі три поля, taskId=observationId і решту provenance; неповні або підмінені
зв'язки відхиляються. Старі regular snapshots без нових полів сумісні.

Повторне використання не запускає ще один probe і не витрачає additionalChecks
діагностичної сесії. Вже виконаний fallback залишається фізичною спробою зі
своїм durable лічильником: він не стає безкоштовним у загальному обліку.
Baseline є історичним входом сесії, а не новим Assessment чи гарантією свіжості
до довільного майбутнього моменту.
