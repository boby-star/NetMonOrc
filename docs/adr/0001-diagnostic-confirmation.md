# ADR 0001: явне підтвердження діагностичного класу

Статус: реалізовано й перевірено у мінімальному прототипі.
[Натурний пілот](../experiments/confirmation-pilot/README.md): 15 запусків, один повтор сценарію.

Пілот ec685e3 підтвердив хибну класифікацію HTTP+DNS як тільки DNS.
Поля AdaptivePolicy.confirmation користувач погодив раніше: actionRefs,
minObservations, minDistinctFailureDomains, minSpacing; stopWhenUnique=false
вимагає явної політики. На цьому етапі retry був окремою нереалізованою функцією; пізніше його
додано в [ADR 0004](0004-bounded-diagnostic-retry.md).

У межах доручення самостійно обирати рекомендовані рішення вибрано
консервативну трактовку: actionRefs — обов'язковий набір, не випадковий вибір
одного підтвердження. Потрібні всі зазначені перевірки з конкретними
success/failure patterns для отриманого класу, загальна кількість доказів,
відомі різні failure domains та часова відстань. Для числових параметрів
підтвердження немає неявних defaults: вони обов'язкові в явному об'єкті.

Gain/Cost і первинний adaptive selector не змінюються. Після одного класу
можна виконувати тільки задані confirmation actions, включно з явно
дозволеним повтором для іншого domain або потрібної кількості доказів.
Кожний запуск витрачає бюджет. Невідомий результат/technical failure не
зараховується; автоматичного technical retry тієї самої пари action/agent через confirmation немає.

Усі ID одного фізичного baseline observation рахуються один раз.
Регулярні результати приймаються тільки після еквівалентного matching з
TTL/revision/zone, а завершення діагнозу після expiry використаного baseline
дає inconclusive. Старі baseline докази не доводять minSpacing: їхній
консервативний часовий рубіж — початок Run. Новий probe відправляється після
інтервалу від підтвердженого приймання попереднього; затримка доставки не
створює штучну незалежність. domain бере Controller, не Agent payload;
у поточному roster це зона мережевого шляху, не незалежність фізичних хостів.

Fixed отримує той самий контроль протоколів через явний чотирикроковий DAG.
Якщо активований крок має technical failure/unknown або CEL condition error,
унікальний залишок класів ще не означає completed: повертається inconclusive.
Звичайний when=false не блокує завершення. Це консервативне уточнення умови
завершення Fixed, а не новий DSL-параметр. Воно внесене до ТЗ/DSL; DOCX
отримує той самий додаток. HTTP API цим етапом не змінюється.

Приклад confirmed-профілю перевіряє DNS з office, а DNS/TCP/HTTP — із server.
Adaptive з підтвердженням і Fixed виконують щонайменше ці чотири перевірки;
Static — весь каталог із шести. Виграш над Fixed не обіцяється: додаткова
ціна за відмову від хибної певності є частиною експерименту. Legacy YAML
лишається доступним; сам старий пілот відтворюється на його source commit.

Підтвердження лише перевіряє сумісність із задекларованим каталогом і
профілем. Несправність, що має той самий pattern, не стає фізично доведеною
причиною. Модель шуму, retries, повторні сесії та silent-drop deadline
профіль ще не завершені.
