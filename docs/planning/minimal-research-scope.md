# NetMonOrc: мінімальний дослідницький прототип

Статус: пропозиція обсягу після аналізу «Чернов С. записка v1.docx».
Це аналітичний документ, а не зміна нормативних ТЗ, DSL або OpenAPI.
Наведені функції заплановані; їх реалізація цим документом не підтверджується.

## 1. Вихідний стан і висновок

У доступному репозиторії на момент перевірки є README, Markdown-ТЗ,
DSL Schema, OpenAPI та DOCX-ТЗ. Вихідного коду застосунків немає.
Доступний commit: `7de9f22` (`Add files via upload`).

Роботу можна поновити як нову реалізацію на основі збережених вимог.
Це не відновлення втрачених файлів і не продовження наявного працездатного коду.
Наданий документ містить розділ 1, підрозділи 2.1–2.2 і заголовки 2.3–2.6.
Реалізація й експериментальні результати в цьому файлі не описані.

У §1.4 прямо поставлено завдання створити **програмний прототип** методу.
Для цього не потрібна вся продуктова платформа з попереднього v1alpha1.
Межі дослідницького прототипу слід явно відрізняти від повної відповідності v1alpha1.

## 2. Обов'язковий результат за запискою

| Джерело | Мінімальна реалізація | Свідчення готовності |
|---|---|---|
| §1.4, §2.1 | YAML-опис цілей, Monitor, профілів, зон, агентів і політик | Коректна конфігурація формує план, некоректна відхиляється з поясненням |
| §1.4, §2.1 | Controller та щонайменше два агенти у різних мережевих зонах стенда | Один ресурс реально перевіряється з обох зон; результати зберігають походження |
| §1.4, §2.1 | ICMP, DNS, TCP, HTTP/HTTPS через Blackbox Exporter | Є реальні позитивні та негативні результати, а недоступність exporter відокремлена від відмови цілі |
| §1.4, §2.2 | Обмежене extraction і CEL без shell execution | Успішний HTTP 200 із неправильним прикладним значенням не стає автоматично healthy |
| §2.1–2.2 | Observation з ID, check, agent, zone, revision, часом, execution status і probe outcome | Дублікати, старі ревізії та прострочені докази не змінюють поточний висновок |
| §2.1–2.2 | Assessment: H, Q, required, TTL, maxSkew, all/any/quorum, зональні й глобальні стани | Втрата агента дає дефіцит покриття, а підтверджена required-відмова — down у відповідній зоні |
| §1.4 | Вибір діагностичної пари «дія–агент», що враховує докази, можливості, зони й бюджет | Видно, чому обрано дію/виконавця, що отримано та чому діагностику завершено |
| §1.4 | Static, Fixed і Adaptive для одного каталогу перевірок | Усі режими запускаються на однакових сценаріях і порівнюваних обмеженнях |
| §1.4, §2.2 | Одне просте сповіщення про зміну стану, журнал рішень | Подія відтворюється й пов'язана з Assessment; достатньо одного webhook |
| §1.4 | Відтворюваний стенд і експорт вимірювань | Сценарії запускаються повторно, результати CSV/JSON придатні для розділу експериментів |

Огляд SNMP, IDS/IPS, аналізу трафіку та можливостей сторонніх платформ у розділі 1
не означає вимоги реалізувати ці функції у NetMonOrc.

## 3. Найменша доцільна архітектура

- Один Controller на Go: конфігурація, призначення, приймання результатів,
  оцінювання, діагностика та доступ до даних.
- Один Agent на Go, розгорнутий у двох чи більше точках стенда:
  отримання завдань, обмеження паралельності, виклик exporter, передавання результатів.
- Blackbox Exporter біля кожного агента для стандартних мережевих перевірок.
  Власний HTTP runner — лише для обмеженого extraction, потрібного прикладу.
- PostgreSQL для історії спостережень, оцінок та діагностичних запусків.
  Власна TSDB, брокер повідомлень і HA не потрібні.
- Docker Compose та конфігурації мереж стенда. Контейнери, які бачать один
  мережевий шлях, самі по собі не підтверджують розподіленість: сегменти повинні
  дозволяти незалежно відтворити недоступність цілі з одного боку.
- YAML є основним способом налаштування. Не потрібен візуальний редактор.
- Для демонстрації доцільна тонка вебпанель: ресурси/стани, зони/агенти,
  деталі діагностики. Повний UI з керуванням користувачами запискою не вимагається.

Для прототипу можна обмежити конфігурацію наявними ресурсами DSL,
потрібними демонстраційним сценаріям. Непідтримувані можливості потрібно
явно відхиляти або документувати як недоступні, а не мовчки ігнорувати.
Target у предметній моделі не слід автоматично перетворювати на новий YAML kind.
Існуючі маршрути API не потрібно перейменовувати заради прототипу.

Замість повного enrollment/UI керування PKI для стенда можна заздалегідь
видати агентам сертифікати. TLS, перевірка ідентичності, контроль дозволених цілей,
таймаути, обмеження відповідей і ресурсів залишаються необхідними.
Конкретні спрощення продуктового контуру мають бути явно описані як межі прототипу.

## 4. Що не потрібно для першого завершеного дослідження

Повний installer, керування PAT/RBAC через UI, автоматичний випуск і ротація
сертифікатів, універсальний CRUD усіх ресурсів, усі варіанти placement,
розвинений ResourceGroup UI, універсальний fallback, складні інтеграції
сповіщень, HA, Kubernetes, SIEM та аналіз пакетів.

Групи й залежності описані в §2.1, тому їх не слід оголошувати реалізованими.
Перший наскрізний сценарій може працювати з одним ресурсом. Для кінцевої версії
слід або додати мінімальне групування/оцінювання за потрібними сценаріями,
або прямо позначити відповідну частину моделі як розширення, не перевірене прототипом.
Так само optional трасування маршруту не є обов'язковою умовою виконання §1.4.

## 5. Неузгодженості записки, які впливають на алгоритм

1. **Таблиця 2.2, неповні all/any.** Для `OK, OK, –` та `OK, –, –`
   таблиця дає `all = OK`; для `FAIL, FAIL, –` та `FAIL, –, –`
   дає `any = FAIL`. Відсутній результат не підтверджує ані успіх усіх,
   ані відмову всіх. Рекомендована логіка: all — failure за хоча б одного failure,
   success лише за всіх запланованих success, інакше unknown;
   any — success за хоча б одного success, failure лише за всіх failure,
   інакше unknown. Coverage обчислюється незалежно. Це пропозиція виправлення,
   а не прихована зміна документа.
2. **Таблиця 2.2, лічильник.** Для `FAIL, FAIL, –` отримано два результати
   з трьох, хоча в таблиці записано «1 з 3».
3. **§2.1, H та Q.** Після формули сказано «Наведені величини є ймовірностями
   несправності», але §2.2 правильно заперечує ймовірнісне трактування.
   Це зважені показники покриття й успішності, а не оцінки ймовірності.
4. **§2.1, формула H.** У DOCX є математичний об'єкт для Q, але немає
   окремої явної формули H. Її потрібно дописати; «така ж формула» недостатньо:

   `Q = sum(w_j * v_j) / sum(w_j)`

   `H = sum(w_j * v_j * h_j) / sum(w_j * v_j)`

   H не визначений за нульового знаменника. Ці формули не замінюють
   контролю required, повноти replicas, зон і придатності доказів.
5. **Рисунок 2.1.** `Observation.success: bool` не відображає розмежування
   execution failure і негативного probe outcome з тексту. Потрібні окремі
   поля; також слід відобразити revision і часові характеристики.
   `Assignment.configVersion: int` на рисунку потрібно пояснити відносно
   effective revision: не вводити паралельну семантику версій без потреби.
6. **§2.3–2.6 не заповнені.** Алгоритм Adaptive, узагальнення та порівняння
   не можна вважати визначеними лише цим DOCX. Вихідною основою може бути
   алгоритм розрізнюваності гіпотез на одиницю вартості з ТЗ §4.9,
   з урахуванням раніше погоджених уточнень. Фінальний текст записки має
   відповідати реально реалізованому алгоритму.

## 6. Експериментальна частина — обов'язкова

Мінімальні сценарії зі §1.4:

1. Штатна робота ресурсу.
2. HTTP-відмова за доступного вузла.
3. Помилка DNS.
4. Закритий TCP-порт.
5. Недоступність із одного сегмента за доступності з іншого.
6. Втрата агента; окремо корисно перевірити відмову exporter.

Для кожного сценарію потрібна зовнішньо задана істина: яка несправність
внесена та коли. Алгоритм не повинен отримувати цю мітку як підказку.
Static, Fixed та Adaptive використовують спільні доступні дії, агентів,
обмеження і критерії висновку. Порядок запусків та повторення повинні
зменшувати вплив кешів, прогріву та випадкових затримок.

Записувати: правильність стану і діагнозу, частку inconclusive, хибні висновки,
час до оцінки/висновку, число фізичних probes, використаний бюджет.
Мережевий трафік можна порівнювати лише за наявності фактичного вимірювання;
costUnits не можна видавати за кількість байтів.

Невідома або множинна несправність повинна залишатись допустимим результатом.
Не слід обіцяти перевагу Adaptive до отримання експериментальних даних.

## 7. Послідовність відновлення розробки

1. Зафіксувати цей мінімальний профіль і виправлення записки; зіставити
   потрібну частину DSL з попередніми погодженими уточненнями.
2. Реалізувати один реальний ланцюг: YAML → Controller → Agent → exporter
   → Observation → Assessment. Почати з HTTP, відразу зберігати походження,
   revision і execution status; потім підключити другу зону та інші протоколи.
3. Завершити придатність доказів, H/Q, required, зональне оцінювання,
   extraction/CEL та прості сповіщення.
4. Додати Static, Fixed, Adaptive, вибір агента, бюджети і пояснення рішень.
5. Підключити перегляд результатів, сценарії стенда, експорт та експерименти.
6. Звірити текст записки з реально працюючою системою та записати обмеження.

Перевірки зосередити на помилкових висновках, TTL/revision/deduplication,
критичних required-перевірках, бюджеті та одному реальному наскрізному сценарії.
Велика кількість тестів сама по собі не є критерієм готовності.

Кожен завершений крок має залишати перевірюваний commit. До накопичення
значного обсягу роботи потрібна перевірена незалежна копія: доступна віддалена
гілка або експортований користувачу Git bundle з усіма актуальними commits.
Локальний commit у тимчасовому workspace не є незалежною резервною копією.

## 8. Критерій завершення

Прототип готовий для задачі записки, коли з документованої конфігурації
запускається реальний стенд, ресурс спостерігається з кількох зон,
обчислення стану пояснюється доказами, три режими діагностики відтворювано
порівнюються, а результати й обмеження перенесені до роботи.

Це не гарантія прийняття роботи кафедрою: у наданому файлі немає окремого
затвердженого завдання кафедри чи формальних критеріїв захисту.
На момент початкового аналізу код був відсутній; попередні відсотки
не характеризували доступний репозиторій. Для нової реалізації актуальні
статус і критерії оцінки наведено в IMPLEMENTATION_STATUS.md та
[prototype-readiness.md](prototype-readiness.md).
